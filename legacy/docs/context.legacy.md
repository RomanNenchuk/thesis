## 1. Проєкт LinkUp

Кросплатформена соціальна мережа з публікаціями, прив'язаними до геолокації. Почалась як курсовий проєкт, тепер — база для диплома.

**Клієнт:** React 18 + TypeScript, Vite, TanStack Router/Query, MUI, Leaflet/React-Leaflet + OpenStreetMap.
**API:** .NET 9 / ASP.NET Core Web API, Clean Architecture (Domain / Application / Infrastructure / Web), PostgreSQL + PostGIS, EF Core, JWT + Google OAuth 2.0, Cloudinary, LocationIQ.

**Наявний функціонал:** автентифікація; стрічка (Recent / Top / Following); пости (до 10 фото, текст до 300 символів, вибір локації на мапі + reverse geocoding); коментарі та лайки; пошук у радіусі; пошук/рекомендації користувачів; профіль із маршрутом по постах; **сторінка аналітики** — heatmap щільності постів + кластеризація постів із медоїдами.

**Ключове обмеження поточної аналітики:** кластеризація **чисто просторова**, зміст/тема поста не враховується. Диплом додає тематичний вимір.

## 3. Дані та поточний стан

**Датасет:** Kaggle `yachaymarketing/text-coordinates-regions` — геотеговані твіти, по одному JSONL-файлу на регіон (`c_<region>.json`), поля включають `text` і `coordinates` (lon, lat). Тексти багатомовні, переважно неформальні й короткі (за змістом — близько до формату постів LinkUp).
❓ Перевірити, чи є в записах timestamp/інші поля (час може дати додатковий вимір, але це поза межами ядра).

**Що вже зроблено в ноутбуці:**

1. Завантаження всіх регіональних файлів в один DataFrame (`region`, `lon`, `lat`).
2. `clean_text`: HTML unescape, видалення URL, `@username`, символу `#` (слово лишається), нормалізація пробілів.
3. Фільтр за довжиною: `word_count >= 4`.
4. Видалення шаблонних/автоматичних текстів (регулярні вирази: check-in, «just posted a photo» багатьма мовами, боти погоди/землетрусів, реферальний спам, релігійні хештег-кампанії).
5. Випадкова підвибірка **100 000** постів, ембеддинги `paraphrase-multilingual-MiniLM-L12-v2`.
6. Пошук k для KMeans (silhouette + elbow): сирі ембеддинги ≈ 0.028, L2-нормалізовані ≈ 0.024, після UMAP (15D, cosine) ≈ 0.3; плато при k ≈ 40–62.
7. Фінал: **UMAP 15D + KMeans, k = 50**; збережено UMAP і KMeans через joblib.
8. Інтерпретація кластерів: топ-слова через TF-IDF зі стоп-словами 10 мов. Вручну позначено ~20+ зрозумілих кластерів (спорт, політика, релігія, COVID, їжа, музика, погода тощо) і ~12 «розмовних/шумових».
9. Порівняльна таблиця 10k vs 100k, висновок про те, що розмір вибірки впливає на гранулярність тем, а не на частку шуму.

**Сильні сторони, які варто зберегти:** ітеративне виявлення ботів/шаблонів і документування цього як самостійного внеску; послідовна логіка «сирі ембеддинги → нормалізація → UMAP»; перевірка змісту кластерів, а не лише метрик.

## 4. Що виправити в поточному ноутбуці

Нижче — те, що треба зробити **до** порівняння методів, бо воно змінює дані або спосіб оцінювання. Пріоритет: P0 — обов'язково, P1 — важливо, P2 — бажано.

| # | Пріор. | Проблема | Що зробити |
|---|---|---|---|
| 1 | P0 | Boilerplate визначається вже **після** видалення URL — втрачено найсильніший сигнал (домен у посиланні: Foursquare/Swarm, Instagram тощо). | Обчислювати `is_boilerplate` по **сирому** `text` (з URL). |
| 2 | P0 | Частина регулярок надто широка: `paylaştı` («поділився») збігається з будь-яким твітом, що містить це слово; `^i'?m at ` ловить реальні пости на кшталт «I'm at home». | Звузити шаблони; оцінити **precision фільтра** на ручній вибірці ~200 видалених постів. Рахувати частку хибних видалень. |
| 3 | P0 | Видалення без сліду. | Не видаляти, а додати прапорець `is_boilerplate`. Тоді «з/без очищення» стає **абляцією** (результат для диплома), а не незворотною дією. |
| 4 | P0 | Немає перевірки на дублікати. MinHash або косинус > 0.95 у ембеддингах); вирішити політику (прибрати/залишити з вагою) і описати. |
| 5 | P0 | Немає стабільного ID посту (`reset_index` губить зв'язок з оригіналом); CSV-збереження ламає переноси рядків/NaN. | Додати `post_id` з вихідних даних; зберігати проміжні таблиці в **parquet**; один фіксований набір `post_id` для 100k підвибірки на всі експерименти. |

## 5. Дослідницькі питання та дизайн експерименту

### Питання

- **RQ1.** Яке подання тексту дає найкращу тематичну структуру для коротких багатомовних геотегованих постів?
- **RQ2.** Який алгоритм кластеризації краще (з k vs без k, з шумом vs без)?
- **RQ3.** Як очищення від шаблонного/автоматичного контенту впливає на результат?
- **RQ4.** Як виявляти просторову концентрацію тем коректно (з поправкою на загальну щільність постів) і чи дає **спільний** простір «тема + координати» кращий результат, ніж двоетапний підхід?

### Чому це не «страшне порівняння всього»

Достатньо контрольованого дизайну. Усі методи проходять **той самий** downstream (однаковий UMAP, однакові метрики, одна підвибірка), змінюється лише один фактор за раз.

| Рівень | Що входить | Коли |
|---|---|---|
| **MVP** (мінімум для захисту) | 3 репрезентації: TF-IDF, MiniLM (є), fastText × KMeans + HDBSCAN; gold-набір; абляція очищення; просторовий аналіз 1 міста з нормалізацією | якщо часу мало |
| **Core** (рекомендовано) | 4 репрезентації (+ сильніший мультимовний енкодер), KMeans + HDBSCAN, абляції (очищення, UMAP), стабільність по seed-ах, просторова частина для 2–3 міст з permutation-тестом | основний план |
| **Stretch** | BERTopic як референс; спільна просторово-тематична кластеризація; валідація через OSM POI; spaCy-лематизація для TF-IDF; GMM/Agglomerative; Сценарій 1 демо | якщо лишиться час |

### Репрезентації тексту

| ID | Метод | Нотатки |
|---|---|---|
| R1 | **TF-IDF** → TruncatedSVD (≈100–300D) → L2-норма | Класичний baseline. Далі той самий UMAP, що й для інших. |
| R2 | **fastText (усереднення векторів слів)** | Варіант: навчити skipgram на всьому очищеному корпусі (один спільний простір, враховує сленг і помилки). Очікувано: **не вирівняний між мовами** → кластери за мовою. Це результат, який треба зафіксувати (мовна ентропія). |
| R3 | **paraphrase-multilingual-MiniLM-L12-v2** | Уже порахований (`embeddings_100k.npy`). |
| R4 | **Сильніший мультимовний енкодер** (напр. `multilingual-e5-base`, `LaBSE` або `paraphrase-multilingual-mpnet-base-v2`) | Обрати один-два. Для e5 потрібен префікс `query: `/`passage: `. Без GPU — Colab/Kaggle. |
| R5 | (Stretch) **BERTopic** end-to-end | Референс-інструмент, а не ще один «метод»: по суті R3/R4 + UMAP + HDBSCAN + c-TF-IDF. |

### Кластеризація та зменшення розмірності

- **Зменшення розмірності:** UMAP 15D, cosine, `min_dist=0.0` — однаково для всіх (+ абляція «без UMAP» для найкращої репрезентації).
- **KMeans:** k зі свіпу (напр. 20, 30, 40, 50, 60, 80), критерій вибору — явний (п. 4, #11).
- **HDBSCAN:** `min_cluster_size` ∈ {50, 100, 200, 500}, `min_samples` — свіп; звітувати **частку шуму** (мітка −1).
- (Stretch) GMM / Agglomerative.

### Абляції

1. З boilerplate / без boilerplate (найкраща конфігурація).
2. З UMAP / без UMAP.
3. (Опційно) 10k / 50k / 100k / більше.
4. (Опційно) порогова довжина поста 3/4/5.

### Про spaCy

Не потрібен у основному пайплайні: трансформерні енкодери працюють на subword-токенах, а для 10+ мов spaCy вимагав би визначення мови + окрема модель на кожну. Єдине розумне застосування — лематизація для en/es/pt у TF-IDF baseline та NER як додаткова ознака. У тексті диплома достатньо **одного обґрунтованого абзацу**, чому його не використано (або Stretch-експеримент).

## 6. Оцінювання (ключовий розділ)

Без розмітки unsupervised-результати важко захищати, тому потрібен **gold-набір**.

### Gold-набір

- 400–600 постів, **випадково** відібраних із очищеної підвибірки (не з кластерів, щоб не було зміщення).
- Фіксована таксономія ~12–15 тем (спорт, політика, релігія, їжа/напої, музика, здоров'я/COVID, погода, фінанси, технології, подорожі/природа, сім'я/стосунки, …) + «розмовне/реакція» + «незрозуміло».
- Розмітка: LLM-попередня розмітка → **ручна перевірка кожного** поста (описати це в тексті). Для надійності — повторна розмітка 50–100 постів через кілька днів (самоузгодженість) або сторонній розмітник для Cohen's κ.
- Обмеження: gold має меншу гранулярність, ніж 50 кластерів → використовувати NMI / V-measure / homogeneity / completeness, а не лише purity (purity зростає з k).

### Метрики

| Метрика | Що вимірює | Порівнянна між репрезентаціями? |
|---|---|---|
| ARI / NMI / V-measure / homogeneity / completeness відносно gold | відповідність людській розмітці | ✅ так |
| NPMI-когерентність топ-слів кластера (gensim) | змістовна цілісність кластерів | ✅ так (залежить від токенізації) |
| Topic diversity (частка унікальних топ-слів) | чи не дублюють кластери один одного | ✅ так |
| **Мовна ентропія** в кластері / частка кластерів із ≥2 мовами | якість кросмовного вирівнювання | ✅ так — головна метрика проти fastText |
| Стабільність: ARI між seed-ами / bootstrap | відтворюваність | ✅ так |
| Частка шуму (HDBSCAN), розподіл розмірів кластерів | поведінка алгоритму | інформативна |
| Silhouette, Davies–Bouldin, Calinski–Harabasz | компактність у **власному** просторі | ❌ ні (лише в межах однієї репрезентації) |
| (Допоміжно) LLM-оцінка когерентності кластера | швидка оцінка суб'єктивної зрозумілості | допоміжна, з описом методики |

(Опційно) слабка супервізія через **хештеги**: взяти топ-N хештегів, видалити їх із тексту й перевірити, чи пости з одним хештегом потрапляють в один кластер.

## 7. Просторова частина (суть Сценарію 2)

Поточний ноутбук — це лише **тематична** кластеризація. Просторова частина ще не зроблена, і саме вона відповідає назві диплома.

### Підготовка

- Обрати **2–3 міста/агломерації** з найбільшою кількістю постів після очищення (визначити з даних). Аналіз у глобальному масштабі безглуздий — теми розподілені за країнами, а не за районами.
- Сітка **H3** (резолюція 8–9, залежно від щільності) або geohash.
- Прив'язати `topic_id` до кожного посту (з найкращої конфігурації розділу 5).

### Головна методологічна пастка

Сира щільність постів певної теми майже повторює **щільність населення/активності** загалом. Тому карта «де багато постів про їжу» покаже просто центр міста. Потрібна нормалізація:

**Location Quotient:** `LQ(t, c) = (n_tc / n_c) / (N_t / N)`, де `n_tc` — постів теми *t* у клітинці *c*, `n_c` — усіх постів у клітинці, `N_t` / `N` — глобальні для міста. LQ > 1 — тема перепредставлена, LQ < 1 — недопредставлена (це і є кейс керівника «активність є, а теми немає»).

### Методи для порівняння

| Підхід | Опис |
|---|---|
| A. Наївний | щільність/кластери лише з постів теми (DBSCAN/HDBSCAN з haversine) — baseline, показати його проблему |
| B. Нормалізований | LQ + згладжування (малі лічильники) + значущість |
| C. Гарячі точки | Getis-Ord Gi* (`esda.G_Local`) по частці теми, Moran's I для глобальної автокореляції |
| D. (Stretch) Спільна кластеризація | вектор `[UMAP-ембеддинг, λ·координати]` → HDBSCAN, свіп λ; порівняти з двоетапним підходом |
| Baseline застосунку | наявна просторова кластеризація з медоїдами сторінки аналітики |

### Статистична перевірка

- **Permutation-тест:** перемішувати мітки тем між постами всередині міста (координати й загальна щільність лишаються) ×999 → null-розподіл для LQ / Gi*; p-значення з поправкою на множинні порівняння (Benjamini–Hochberg).
- Стабільність гарячих точок на підвибірках.

### (Stretch) Зовнішня валідація через OSM

Порівняти карти тем із щільністю POI з OpenStreetMap: їжа ↔ `amenity=restaurant/cafe`, спорт ↔ стадіони/`leisure=pitch`, здоров'я ↔ лікарні, подорожі ↔ аеропорти/пляжі. Spearman-кореляція по клітинках. Це сильний аргумент «метод знаходить реальні речі».

## 9. Інтеграція в застосунок (наприкінці)

💡 Варіант архітектури:

- **Python-мікросервіс (FastAPI)** з артефактами найкращої моделі; .NET API викликає його при створенні/редагуванні поста й отримує `topic_id` (+ ймовірно топ-слова теми).

**Ризики:** зсув домену (твіти 2021 року vs реальні пости LinkUp — малий обсяг, інший стиль), холодний старт з малою кількістю постів у конкретному районі, затримка інференсу на CPU, мовне покриття.

## 11. Ризики та обмеження (згадати в тексті)
